# Архитектура «Домового»

## Обзор

«Домовой» разворачивается как монорепозиторий и один Docker Compose-проект для одной семьи. Пять
сервисов работают без внешнего оркестратора и Redis. Этап 2 добавляет постоянную модель семьи и
серверный контур идентификации, не меняя топологию контейнеров.

| Сервис | Назначение | Доступ извне |
| --- | --- | --- |
| `proxy` | Caddy, единая HTTP/HTTPS-точка входа | 80/TCP, 443/TCP и 443/UDP |
| `frontend` | собранное React PWA, выдаваемое Nginx | нет |
| `api` | версионируемый FastAPI `/api/v1` | нет |
| `worker` | фоновые периодические и служебные задания | нет |
| `database` | PostgreSQL | нет |

Все сервисы находятся в закрытой bridge-сети Compose. Caddy направляет `/api/*` и `/health/*` в
API, остальные запросы — во frontend.

## Структура репозитория

```text
apps/
  api/                 FastAPI, SQLAlchemy, Alembic и worker
  frontend/            React, TypeScript, Vite и PWA
deploy/caddy/           Конфигурация reverse proxy
docs/                   Спецификация, архитектура и дизайн-референс
scripts/                Подготовка окружения и сквозная проверка Compose
compose.yaml             Production-like локальная оркестрация
```

## Серверная часть

API использует асинхронный SQLAlchemy и драйвер `asyncpg`. Миграции Alembic запускаются
entrypoint-скриптом до старта Uvicorn, поэтому API не начинает принимать запросы со старой схемой.
Готовность проверяется отдельным запросом `SELECT 1`; liveness не зависит от базы.

Worker собирается из того же Python-образа, но запускает отдельный процесс. На первом этапе он
делает устойчивую к ошибкам проверку базы по таймеру. На Этапе 2 тот же идемпотентный цикл удаляет
только давно истёкшие/отозванные сессии и старые записи ограничения входа. Доменные расписания
добавляются последующими этапами без объединения worker с веб-процессом.

## Идентификация и семья

Миграция `0002_identity_and_family` создаёт:

| Таблица | Назначение |
| --- | --- |
| `households` | Единственный дом установки, язык, часовой пояс и начальные уведомления |
| `users` | Логин, роль, Argon2id-хеш пароля/PIN, цвет, активность и состояние временного пароля |
| `sessions` | Срок, отзыв, клиент и HMAC-SHA256-хеш непрозрачного токена |
| `trusted_devices` | Доверенные браузеры общих планшетов без хранения исходного токена |
| `absences` | Диапазоны отсутствия и необязательный временный заместитель |
| `login_attempts` | Короткоживущие записи для ограничения перебора логина и PIN |

Первый `household` защищён уникальным singleton-ограничением. Поэтому два параллельных запроса
мастера не могут создать две семьи. Логины нормализуются в нижний регистр и уникальны в пределах
всей установки.

Пароли и PIN хешируются Argon2id и никогда не возвращаются после сохранения. Случайный временный
пароль возвращается администратору ровно в ответе создания/сброса. В базе хранятся только его хеш и
признак обязательной смены.

Обычный вход создаёт 256-битный случайный session token. Клиент получает его в HttpOnly cookie с
`SameSite=Strict`, а PostgreSQL — только HMAC-SHA256 digest с ключом установки. Отдельный CSRF token
передаётся в читаемой cookie и обязан совпасть с заголовком `X-CSRF-Token` и digest в сессии для
изменяющих запросов. При HTTPS используется `COOKIE_SECURE=true`; HTTP по IP требует `false`.

Пять неудачных попыток одной пары логин/IP за 15 минут временно блокируют обычный вход; тот же
механизм отдельно защищает PIN конкретного пользователя на планшете. Сообщение об ошибке входа не
раскрывает, существует ли логин или отключена ли учётная запись.

Права проверяются зависимостями FastAPI на сервере. Читать базовый список семьи может любой активный
пользователь. Создание, отключение, сбросы, PIN, сессии, отсутствия и доверенные устройства доступны
только администратору. Сброс пароля и отключение атомарно отзывают активные сессии.

Доверенное устройство имеет отдельную долгоживущую HttpOnly cookie. Только пользователь с заданным
PIN появляется на экране выбора аватара. Успешный PIN создаёт обычную ограниченную ролью сессию,
связанную с устройством; отзыв доверия завершает все такие сессии.

Первая миграция создаёт `system_metadata`. Она служит минимальной постоянной записью схемы и
проверкой сохранности PostgreSQL volume.

## Клиент

Клиент — React PWA со строгим TypeScript. Manifest и service worker формируются Vite PWA plugin.
Приложение использует локально поставляемые Manrope и Inter, дизайн-токены из спецификации,
системную тёмную тему, адаптивную боковую/нижнюю навигацию, клавиатурный фокус и
`prefers-reduced-motion`.

Русские интерфейсные строки собраны в `src/lib/i18n.ts` как начальная граница будущей локализации.
Мастер, вход, обязательная смена временного пароля, режим планшета и экран семьи используют живой
API. Показанные на «Сегодня» задачи остаются интерактивными демонстрационными данными shell до
Этапа 3.

## Данные и volumes

- `database_data` — PostgreSQL;
- `user_files` — пользовательские вложения;
- `backup_data` — месячные и ручные архивы;
- `caddy_data`, `caddy_config` — сертификаты и внутреннее состояние Caddy.

Удаление контейнеров не удаляет volumes. Команда `docker compose down -v` является разрушительной и
не используется в инструкциях обновления.

## Конфигурация и секреты

Compose имеет безопасные для локальной проверки значения по умолчанию, однако установка на сервер
обязана сначала выполнить `./scripts/setup-env.sh http://IP`, который создаёт `.env` с режимом 600 и
криптографически случайными значениями. `.env` исключён из Git.

`APP_ADDRESS=http://IP` и `COOKIE_SECURE=false` оставляют HTTP для первого запуска. Значения
`APP_ADDRESS=home.example.org` и `COOKIE_SECURE=true` переключают Caddy на автоматический публичный
TLS и защищённые cookies. Полный сценарий перенаправления IP и обновления относится к Этапу 9.

## Наблюдаемость

Python пишет структурированные JSON-логи в stdout. В них не должны попадать секреты и приватные
данные. Compose health checks проверяют PostgreSQL, API, worker и frontend; proxy запускается только
после готовности upstream-сервисов.
