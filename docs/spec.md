# Мастер-промт для Codex: семейное приложение «Домовой»

Ты работаешь над полноценным self-hosted веб-приложением «Домовой» для домашних дел, покупок, хранения вещей и обслуживания дома. Это не демонстрационный макет: результат должен запускаться на Linux-сервере через Docker Compose, сохранять данные между перезапусками и быть пригодным для ежедневного использования одной семьёй.

## 1. Главный порядок работы

1. Сначала изучи репозиторий:
   - прочитай AGENTS.md и другие инструкции, если они есть;
   - проверь существующую архитектуру, файлы, зависимости, незакоммиченные изменения и тесты;
   - сохраняй пользовательские изменения и не переписывай их без необходимости;
   - если репозиторий пустой, создай проект с нуля.
2. Составь короткий рабочий план только для текущего этапа.
3. Реализуй только текущий этап из раздела «Этапы разработки».
4. Не ограничивайся заглушками и статичными макетами. Всё заявленное для этапа должно работать сквозным образом: интерфейс, API, база данных, права и тесты.
5. После этапа:
   - запусти форматирование, линтеры, типизацию, тесты и production-сборку;
   - проверь Docker Compose и миграции, если они затронуты;
   - обнови README и техническую документацию;
   - перечисли реализованное, результаты проверок и известные ограничения;
   - сделай отдельный локальный Git-коммит с понятным сообщением;
   - остановись и жди явного подтверждения пользователя.
6. Никогда не переходи к следующему этапу автоматически, даже если текущий прошёл успешно.
7. Не выполняй git push, не создавай pull request и не разворачивай приложение на внешнем сервере без отдельного разрешения.
8. Если встречается действительно блокирующий выбор, задай один конкретный вопрос. Неблокирующие детали решай разумно, фиксируя решение в документации.

Начни с Этапа 1. После его завершения остановись.

## 2. Назначение и границы продукта

«Домовой» — русскоязычное семейное PWA для:

- домашних дел и повторяющихся обязанностей;
- распределения ответственных;
- списков покупок;
- уведомлений;
- учёта вещей и мест хранения;
- QR-кодов мест хранения;
- обслуживания дома, техники, ремонтов, гарантий и счётчиков;
- календаря семьи;
- ограниченной офлайн-работы.

Одна установка обслуживает одну семью и один общий «дом», но внутри можно создавать несколько физических объектов: квартиру, дом, дачу, гараж, сарай и другие зоны.

Ожидаемый масштаб одной установки:

- не менее 20 пользователей;
- до 50 000 карточек вещей;
- не менее 100 000 завершённых экземпляров задач;
- объём файлов ограничивается диском сервера.

## 3. Обязательный технологический стек

Используй совместимые актуальные стабильные версии и зафиксируй их lock-файлами.

- Frontend: React, TypeScript, Vite.
- Формат клиента: адаптивное PWA.
- Backend: Python, FastAPI.
- База данных: PostgreSQL.
- ORM и миграции: SQLAlchemy и Alembic.
- Фоновая обработка: отдельный Python worker для расписаний, уведомлений, очистки и резервных копий.
- Reverse proxy и HTTPS: Caddy.
- Оркестрация: Docker Compose.
- Целевые архитектуры контейнеров: amd64 и arm64.
- Redis в первой версии не использовать.
- Файлы в первой версии хранить на локальном диске сервера в отдельном Docker volume.
- S3 и MinIO в первой версии не использовать.

Сервисы Compose:

- frontend;
- api;
- worker;
- database;
- proxy.

База, worker и внутренний API не должны быть напрямую опубликованы в интернет. Снаружи открываются только 80 и 443 через Caddy.

## 4. Развёртывание и первый запуск

Приложение устанавливается на Linux-сервер универсальным Docker-пакетом.

Требования:

- запуск одной документированной командой Docker Compose;
- постоянные volumes для PostgreSQL, пользовательских файлов и резервной копии;
- health checks и разумные restart policies;
- секреты генерируются при установке и не хранятся в исходном коде;
- пример безопасного env-файла без реальных секретов;
- вначале приложение можно открыть по IP-адресу;
- позже администратор подключает домен;
- после подключения домена Caddy автоматически получает TLS-сертификат;
- обращения по IP перенаправляются на домен после его настройки;
- PWA Web Push включается после появления HTTPS;
- часовой пояс установки настраивается и везде обрабатывается последовательно.

При первом запуске покажи мастер настройки:

1. язык и часовой пояс;
2. создание первого администратора;
3. название дома;
4. настройка уведомлений;
5. необязательный импорт архива старой версии.

Нужен безопасный сценарий обновления:

- перед обновлением создать временную страховочную копию;
- применить миграции;
- запустить проверки работоспособности;
- удалить временную копию только после успешных проверок;
- при ошибке выполнить безопасный откат.

## 5. Роли, вход и пользователи

Роли:

- Администратор;
- Взрослый;
- Ребёнок.

Правила:

- публичной регистрации и самостоятельного создания семьи нет;
- первого администратора создаёт мастер первоначальной настройки;
- последующих пользователей вручную создаёт только администратор;
- поля пользователя: имя, уникальный логин, роль, временный пароль, аватар или цвет;
- взрослый обязан сменить временный пароль при первом входе;
- для ребёнка обязательность смены временного пароля настраивается;
- восстановление пароля выполняет администратор, email для восстановления не обязателен;
- отключение учётной записи сохраняет связанные данные;
- администратор может завершить активные сессии пользователя;
- пароли хранятся только как стойкие современные хеши;
- нужны rate limiting, защита входа и серверная проверка разрешений на каждом действии.

Права ребёнка:

- видеть свои и общие задачи;
- завершать назначенные ему задачи;
- брать задачи со статусом «может выполнить любой»;
- предлагать товары в покупки;
- просматривать кладовую;
- нажимать «Использовано сегодня» в карточке вещи;
- не может изменять или удалять чужие записи;
- не имеет доступа к системным настройкам, резервным копиям и финансовым документам.

Общий семейный планшет:

- администратор регистрирует доверенное устройство;
- на устройстве показывается выбор пользователя по аватару;
- вход выполняется коротким PIN;
- поддерживается быстрое переключение пользователей;
- обычные персональные устройства используют логин и пароль.

Временное отсутствие пользователя:

- даты начала и окончания;
- отсутствующего пропускают настроенные очереди;
- закреплённые задачи можно временно передать другому;
- по окончании периода пользователь автоматически возвращается в очереди.

## 8. Экран «Сегодня»

В заголовке показывай только приветствие и дату. Строку вида «Семья Ворониных» не показывать.

На вкладке «Сегодня» не должно быть отдельного окна, карточки или виджета кладовой.

Порядок задач:

1. просроченные;
2. задачи с указанным временем;
3. задачи без времени;
4. завершённые — в свёрнутом блоке.

Есть переключатель «Мои / Все». Выбор запоминается для конкретного устройства.

Прогресс дня считает только задачи и не включает покупки.

Блок покупок показывается только тогда, когда на текущий день запланирован поход в магазин или заказ. В нём сначала показываются товары «Для меня», затем «Общие». Если ответственный покупает и для других членов семьи, ниже идут группы этих пользователей.

Просроченное обслуживание и истёкший таймер хранения появляются как обычные задачи, а не отдельные специальные виджеты.

## 9. Дела

Поля задачи:

- название;
- описание;
- комната или зона;
- категория;
- дата и время выполнения;
- примерная длительность;
- приоритет;
- один или несколько ответственных;
- подзадачи;
- повтор;
- напоминания;
- необходимость фото-подтверждения;
- необходимость проверки взрослым;
- история выполнения.

Варианты повторов:

- каждый день;
- выбранные дни недели;
- еженедельно;
- ежемесячно;
- ежегодно;
- каждые N дней, недель, месяцев или лет;
- через заданный период после предыдущего выполнения;
- определённый день месяца;
- сезонный;
- без повтора.

Взрослый завершает обычную задачу сразу. Для задачи ребёнка можно включить проверку взрослым. Взрослый может отклонить результат с комментарием. Фото-подтверждение включается отдельно у конкретной задачи.

Назначение по умолчанию ручное.

Не реализовывать автоматическое назначение по принципу «у кого меньше нагрузка».

Дополнительно у задачи можно включить настроенную очередь:

- администратор или взрослый выбирает упорядоченный список участников;
- участники идут по кругу;
- очередь сдвигается после выполнения либо ручного пропуска администратором;
- отсутствующие пользователи автоматически пропускаются;
- порядок можно менять, участников можно заменять;
- интерфейс показывает текущего и следующего;
- просроченная задача остаётся у текущего ответственного;
- одновременно существует только один открытый экземпляр одной повторяющейся задачи.

Также поддержать:

- фиксированного ответственного;
- «может выполнить любой»;
- нескольких ответственных.

Экран «Все дела»:

- вкладки «Активные», «Завершённые», «Повторяющиеся»;
- фильтры по пользователю, категории, комнате, статусу, периоду и повтору;
- группы «Просрочено», «Сегодня», «На этой неделе», «Позже», «Без даты»;
- представление списком;
- Kanban не нужен.

## 10. Покупки

Список покупок может быть:

- общим списком без даты;
- запланированным походом в магазин или заказом.

Поля списка:

- название;
- магазин;
- дата и время;
- ответственный;
- статус;
- комментарий.

Статусы:

- без даты;
- запланирован;
- в процессе;
- завершён.

Поля товара:

- название;
- количество и единица;
- категория;
- заметка;
- кто добавил;
- получатель: конкретный член семьи или «Общее»;
- куплен или не куплен;
- необязательные фото, цена и магазин.

Свёрнутая строка покупки показывает только:

- название;
- количество;
- получателя;
- флажок «Куплено».

Дополнительная информация отображается только после раскрытия строки. Если дополнительных данных нет, не показывай пустые поля и вообще не показывай кнопку раскрытия.

Во вкладке «Сегодня» сначала показываются товары текущего пользователя, потом общие, а затем при необходимости группы других членов семьи.

Экран «Покупки»:

- вкладки «Текущие», «Запланированные», «История»;
- отдельная вкладка запросов детей видна взрослым и администратору;
- группировка по получателю;
- внутри группы сортировка по категории магазина.

Ребёнок добавляет предложение, которое ждёт решения взрослого. Взрослый может принять или отклонить его.

Нужны:

- предупреждение о возможных дублях;
- быстрое добавление часто покупаемых товаров;
- при завершении списка вопрос, что сделать с некупленными позициями;
- необязательные цены и сумма за переключателем модуля;
- офлайн-режим похода в магазин с крупными элементами управления.

Сканирование штрихкодов в первой версии не требуется.

## 11. Кладовая и хранение вещей

Кладовая представляет собой неограниченное дерево. Пример:

- Дом;
  - Чердак 1;
    - Стеллаж;
      - Полка;
        - Коробка;
  - Чердак 2.

Пользователь создаёт произвольные типы разделов:

- помещение;
- чердак;
- подвал;
- гараж;
- шкаф;
- стеллаж;
- полка;
- ящик;
- коробка;
- контейнер;
- другое.

В каждом узле одновременно могут находиться:

- дочерние разделы;
- карточки вещей непосредственно в этом узле.

На компьютере слева показывается дерево, справа содержимое текущего узла. На телефоне используется breadcrumb. Сначала показывай дочерние разделы, затем вещи текущего уровня.

Действия:

- создать раздел;
- добавить вещь;
- найти;
- отсканировать QR;
- создать или скачать QR раздела;
- выбрать несколько объектов;
- переместить;
- изменить порядок.

На компьютере можно использовать drag-and-drop. На телефоне обязательно должна быть понятная кнопка «Переместить».

Групповые операции:

- перемещение;
- смена категории;
- смена владельца;
- установка таймера хранения;
- архивация.

### Поиск в кладовой

- поиск с корня охватывает всё дерево;
- в конкретном разделе и на странице из QR есть переключатель «Здесь и ниже / Только этот уровень»;
- искать по названию, категории, описанию, тегам, владельцу, серийному номеру, разделу и контейнеру;
- результат всегда показывает полный путь до вещи;
- отдельного глобального поиска приложения нет.

### Карточка вещи

Каждая вещь — отдельная карточка только в одном месте. Одинаковые вещи в разных местах — разные карточки.

Обязательное поле:

- название.

Необязательные поля:

- фотографии;
- количество и единица;
- категория;
- владелец;
- описание;
- теги;
- состояние или статус;
- дата размещения;
- дата последнего использования;
- стоимость;
- дата покупки;
- производитель и модель;
- серийный номер;
- гарантия;
- комментарий.

Свёрнутая карточка показывает:

- основное фото;
- название;
- количество;
- сколько времени вещь находится в текущем месте;
- последнее использование;
- состояние таймера хранения.

После раскрытия доступны:

- «Использовано сегодня»;
- «Переместить»;
- «Продлить хранение»;
- «Изменить».

Кнопка «Использовано сегодня» обновляет только дату последнего использования. Она никогда не перезапускает, не продлевает и не изменяет таймер хранения.

Статусы:

- хранится;
- используется;
- временно взято;
- одолжено;
- потеряно;
- продано;
- выброшено.

Историю перемещений не хранить. При перемещении:

- меняется текущее местоположение;
- счётчик времени в текущем месте начинается заново;
- крайний срок таймера хранения не меняется, пока пользователь не изменит его вручную.

### Таймер хранения

У карточки можно необязательно задать:

- N дней, месяцев или лет;
- конкретную дату пересмотра.

По истечении:

- статус становится «Нужно решить»;
- создаётся обычная задача на вкладке «Сегодня».

Варианты решения:

- продлить;
- убрать таймер;
- переместить;
- продать;
- отдать;
- выбросить;
- удалить.

### QR-коды

- QR создаётся вручную по желанию для любого раздела или контейнера;
- QR содержит стабильную ссылку или токен, не зависящий от списка содержимого;
- добавление, удаление и редактирование содержимого никогда не меняет QR;
- только явное действие «Пересоздать QR» выпускает новый код и аннулирует старый;
- QR требует авторизации;
- после входа пользователь возвращается в нужный раздел;
- QR чердака показывает содержимое чердака, включая вложенные уровни;
- QR коробки показывает содержимое коробки;
- QR можно скачать и распечатать;
- публичного режима QR нет;
- на странице содержимого из QR также есть поиск.

## 17. Резервные копии, экспорт, импорт и перенос версий

Автоматическая копия:

- хранится ровно одна месячная копия;
- новая копия заменяет предыдущую только после проверки целостности;
- замена атомарная;
- если создание или проверка новой копии не удались, старая остаётся;
- копия находится в отдельном volume.

Ручной переносимый экспорт:

- администратор может сделать в любое время;
- такие архивы не удаляются автоматически.

Архив включает:

- пользователей и хеши паролей;
- задачи и историю;
- покупки;
- кладовую;
- обслуживание;
- файлы;
- настройки;
- стабильные идентификаторы QR;
- версии приложения и схемы;
- контрольные суммы.

Импорт:

1. проверить целостность и совместимость версии;
2. сделать страховочную копию текущего состояния;
3. последовательно применить миграции;
4. восстановить файлы;
5. проверить количество и целостность данных;
6. показать отчёт.

После восстановления аннулировать активные сессии. Стабильные QR должны продолжать работать после переноса версии. Восстановление требует подтверждения паролем администратора.

## 18. Офлайн, realtime и конфликты

Ограниченный офлайн-режим первой версии:

- кэшированная вкладка «Сегодня»;
- запланированный список покупок;
- отметка товара купленным;
- добавление товара;
- завершение задачи;
- недавно открытые разделы кладовой только для чтения;
- синхронизация при восстановлении сети.

Офлайн нельзя:

- управлять пользователями;
- менять системные настройки;
- работать с резервными копиями;
- загружать файлы;
- управлять QR;
- выполнять поиск по всей кладовой.

Изменения с других устройств появляются без перезагрузки. Используй оптимистичный интерфейс с обязательным подтверждением сервера.

Правила конфликтов:

- изменения разных полей одной карточки объединяются автоматически, если это безопасно;
- одновременное изменение одного поля создаёт конфликт;
- карточка подсвечивается красным и получает статус «Конфликт синхронизации»;
- действующей остаётся последняя подтверждённая сервером версия;
- альтернативное изменение сохраняется;
- пользователь с правом редактирования выбирает: оставить серверную версию, принять новую или объединить вручную;
- при пяти и более нерешённых конфликтах администратор получает одно уведомление и видит центр конфликтов;
- администратор может отклонить все ожидающие изменения либо разбирать их по одному;
- автоматического принятия или удаления конфликтующих вариантов нет;
- другие пользователи могут разрешать отдельные конфликты, если имеют право редактировать соответствующую запись.

Общей ленты активности не нужно. В раскрытой карточке можно показать короткую строку «Изменено: пользователь, время».

QR удалённого раздела перестаёт работать после окончательного удаления. Если раздел восстановлен из корзины в течение 30 дней, прежний QR снова работает.

- адаптивные E2E или визуальные проверки ключевых экранов.

Критические E2E-сценарии:

1. Первый администратор проходит мастер настройки и создаёт взрослого и ребёнка.
2. Взрослый создаёт повторяющуюся задачу с очередью, ребёнок выполняет, взрослый подтверждает.
3. Запланированные на сегодня покупки появляются в «Сегодня», незапланированные не появляются.
4. Ребёнок предлагает товар, взрослый принимает его.
5. Пользователь создаёт дерево кладовой, карточку вещи и стабильный QR, затем меняет содержимое без изменения QR.
6. Истекает таймер хранения и создаётся обычная задача.
7. Обслуживание оборудования создаёт задачу и после выполнения попадает в историю.
8. Два устройства одновременно меняют одно поле, карточка становится красной до ручного решения.
9. Покупки и завершение задачи работают офлайн и синхронизируются после reconnect.
10. Экспорт из старой версии импортируется в новую с сохранением файлов и QR.

## 26. Формат отчёта после каждого этапа

Ответ должен быть коротким и проверяемым:

1. Что реализовано.
2. Какие ключевые файлы изменены.
3. Какие команды проверок выполнены и их результат.
4. Что осталось за пределами текущего этапа.
5. Хеш и сообщение локального коммита.
6. Явная фраза: «Этап N завершён. Жду вашего подтверждения перед переходом к этапу N+1».

Если этап не завершён, не создавай фиктивный успешный отчёт. Чётко опиши блокер, незавершённые пункты и необходимые действия.
